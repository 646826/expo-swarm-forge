# Canyon Charms и SwarmForge: учебное руководство

Это руководство предназначено для школьной команды, которая хочет создать небольшую браузерную игру профессиональным способом: сначала договориться о результате, затем написать проверку, реализовать поведение, проверить игру глазами игрока и только после этого публиковать.

## 1. Что мы строим

В репозитории есть две части.

**Шаблон** помогает начать новую игру. Команда получает готовые команды сборки, тестов, локального сервера, упаковки и четыре роли SwarmForge.

**Canyon Charms** показывает законченный пример. Это оригинальная match-3 игра: игрок меняет местами соседние талисманы, собирает линии, создаёт фейерверки и динамит, запускает каскады и набирает 5 000 очков за 20 ходов.

## 2. Команда SwarmForge

### Director

Уточняет цель, делит работу на маленькие результаты, принимает спецификацию, следит за порядком коммитов и решает, когда можно выполнять merge.

### Gameplay

Отвечает за чистые правила: поле, допустимые ходы, совпадения, каскады, очки, специальные элементы и победу. Сначала пишет тест, который падает по правильной причине.

### Presentation

Показывает состояние игры: Canvas, анимация, частицы, звук, управление, меню и доступность. Не придумывает собственные правила.

### QA

Проверяет игру через пользовательский интерфейс, разные размеры окна, клавиатуру, touch, паузу, reduced motion, сборку и публикационный пакет.

## 3. Главный цикл работы

```text
Идея игрока
    ↓
Точный пример поведения
    ↓
Падающий тест
    ↓
Минимальная реализация
    ↓
Зелёный тест
    ↓
Улучшение структуры без изменения поведения
    ↓
Браузерная проверка и скриншот
    ↓
Коммит и handoff следующей роли
```

Пример: «Неверная перестановка возвращается обратно и не тратит ход».

1. Gameplay создаёт поле и тестирует число ходов до и после неверной перестановки.
2. Тест падает, потому что функции ещё нет.
3. Gameplay добавляет минимальную проверку соседства и совпадения.
4. Presentation получает событие `swap-back` и показывает обратную анимацию.
5. QA нажимает две неподходящие фишки в браузере и убеждается, что счётчик ходов не изменился.

## 4. Почему правила отделены от графики

Игровое ядро не знает, что такое Canvas, кнопка, звук или Arkadium. Оно получает обычные данные и возвращает новые данные.

```js
const result = attemptSwap(state, firstCell, secondCell);
```

Поэтому правила можно проверить в Node за доли секунды. Позже Canvas можно заменить Phaser, а правила останутся прежними.

## 5. Как устроено поле

Поле — это массив из 64 элементов. Индекс клетки вычисляется так:

```text
index = row × 8 + column
```

При создании поля генератор не разрешает поставить третий одинаковый талисман сразу после двух слева или двух сверху. После заполнения программа дополнительно проверяет, что существует хотя бы один допустимый ход.

## 6. Детерминированность

Псевдослучайный генератор получает `seed`. Одинаковый seed и одинаковые действия дают одинаковую игру.

Это важно для:

- воспроизведения ошибки;
- честного сравнения результатов;
- автоматических тестов;
- записи и повторения партии;
- работы нескольких агентов над одной задачей.

## 7. Совпадения и каскады

Программа отдельно сканирует строки и столбцы. Все серии длиной три и больше становятся match-группами. Пересекающиеся горизонтальные и вертикальные серии объединяются в T/L-группу.

После очистки элементы падают вниз, пустые места заполняются сверху, затем поиск совпадений повторяется. Глубина каскада увеличивает множитель награды.

## 8. Специальные талисманы

- Четыре по горизонтали создают горизонтальный фейерверк.
- Четыре по вертикали создают вертикальный фейерверк.
- Пять, T или L создают динамит.
- Если специальный талисман попал в очищаемую область, его эффект расширяет множество клеток.
- Каждый специальный элемент активируется не более одного раза в одной цепочке.

## 9. Графика без внешних картинок

Все элементы рисуются командами Canvas: градиентами, линиями, кругами и кривыми. Это даёт чистое происхождение ассетов и очень маленький пакет.

Визуальные слои:

1. небо и солнечное свечение;
2. силуэты каньона;
3. деревянная и латунная рамка;
4. камни-талисманы;
5. символы разных форм;
6. выбор, keyboard focus и подсказка;
7. вспышки, частицы и подписи очков;
8. DOM-меню поверх игрового мира.

## 10. Доступность

Хорошая игра не ограничивается мышью.

- Стрелки перемещают фокус.
- Enter или Space выбирают талисман.
- Escape ставит игру на паузу.
- M включает и выключает звук.
- Screen reader получает сообщения о выборе, ходе, комбо и результате.
- Цвет дополняется формой символа.
- Reduced motion уменьшает параллакс, частицы и shake.

## 11. Publisher boundary

Игра умеет работать полностью самостоятельно. Если издательский SDK появится позже, только один adapter передаёт события загрузки, старта, паузы, результата, очков и аналитики.

SDK может отсутствовать, загружаться медленно или вернуть ошибку — игра всё равно должна запускаться. Настоящие `gameId`, credentials и подтверждение издателя нельзя придумывать и нельзя хранить в репозитории.

## 12. Основные команды

```bash
npm test
npm run check -- --project example/canyon-charms
npm run build -- --project example/canyon-charms
npm run package -- --project example/canyon-charms
npm run serve -- example/canyon-charms 4173
```

## 13. CI/CD

GitHub Actions повторяет важные проверки на чистой машине. Pages workflow:

1. получает точный commit;
2. устанавливает Node;
3. запускает тесты и static check;
4. собирает игру;
5. генерирует PDF;
6. загружает только проверенный `dist`;
7. публикует GitHub Pages;
8. возвращает реальный URL deployment.

## 14. Практические задания

### Начальный уровень

1. Добавьте новый цвет фона, не меняя правила.
2. Измените цель уровня через параметры `createGame`.
3. Добавьте новый звуковой сигнал для комбо.
4. Напишите тест, что диагональные клетки нельзя менять местами.

### Средний уровень

1. Добавьте второй уровень с 18 ходами и целью 7 000.
2. Добавьте кнопку Hint, используя существующую `findHint`.
3. Запишите seed неудачной партии и воспроизведите её тестом.
4. Создайте новый специальный элемент сначала через падающий тест.

### Командный уровень

1. Gameplay создаёт поведение и тест.
2. Presentation добавляет только визуальное отображение события.
3. QA пишет браузерный сценарий и прикладывает скриншот.
4. Director проверяет diff, команды и порядок коммитов перед merge.

## 15. Правила хорошего handoff

Handoff должен быть коротким и проверяемым:

```text
type: git_handoff
to: qa
priority: 20
task: invalid-swap-does-not-spend-move
commit: abcdef1234
```

Получатель открывает указанный commit, запускает проверки и не полагается на обещание отправителя.

## 16. Что означает «готово»

Задача готова не тогда, когда код выглядит правдоподобно, а когда есть свежие доказательства:

- тест падал до реализации и проходит после неё;
- полный набор тестов зелёный;
- сборка завершилась с кодом 0;
- браузерный сценарий выполнен;
- интерфейс проверен на desktop и phone;
- commit и артефакты совпадают;
- внешние блокеры честно перечислены.

Так маленькая школьная игра превращается в профессиональный, воспроизводимый проект.
